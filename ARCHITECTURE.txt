HEALTH PIPELINE — ARCHITECTURE & DESIGN EXPLANATION
=====================================================
Written for interview reference: explains the Python, DuckDB, API, and endpoint logic.


WHAT THIS PROJECT IS
---------------------
A lightweight personal health data pipeline built entirely in Python.
It receives health metric exports from an iPhone/Apple Watch, stores them
in a local analytical database, and exposes aggregated summaries through
a REST API — all running on a local Linux machine.


THE STACK
----------
  Python 3.12    — application language
  FastAPI        — web framework for building the REST API
  Uvicorn        — ASGI server that runs FastAPI (handles HTTP connections)
  DuckDB         — embedded analytical database (stores and queries the data)


WHY FASTAPI?
------------
FastAPI is an async Python web framework designed for building APIs quickly.
It uses Python type hints to auto-generate request validation and documentation.
"Async" means it can handle multiple requests concurrently without blocking —
important when a large health export is being written to the DB while another
request comes in for a summary.

Uvicorn is the server layer that sits in front of FastAPI and manages the
actual TCP connections over HTTP.


WHY DUCKDB?
-----------
DuckDB is an embedded OLAP (Online Analytical Processing) database — meaning
it runs inside the Python process with no separate server to manage. It is
designed for analytical workloads: fast aggregations (AVG, SUM, GROUP BY)
over large columnar datasets.

For this project it is ideal because:
  - No database server to install or manage (just a .db file)
  - Handles batch inserts efficiently via executemany()
  - Excels at the aggregation queries used in the summary endpoint
  - The health_data.db file is portable and self-contained

Trade-off: DuckDB only allows one writer at a time. To handle this safely,
the app opens a fresh connection per request and closes it when done, rather
than sharing a single global connection across concurrent requests.


THE DATA MODEL
--------------
A single table: health_metrics

  Column       Type    Description
  ----------   ------  ------------------------------------------
  date         TEXT    Timestamp of the measurement
  metric       TEXT    Name of the metric (e.g. "heart_rate")
  value        FLOAT   The measured quantity
  unit         TEXT    Unit of measurement (e.g. "count/min", "kcal")
  inserted_at  TEXT    When the record was written to the database

This is a "long" or "narrow" table design — every metric gets its own row
rather than having a column per metric. This makes it easy to add new metrics
without changing the schema, and it allows uniform GROUP BY queries across
all metric types.


THE ENDPOINTS
-------------

POST /health
  Purpose:    Receive a health data export from the Apple Health app
  Input:      JSON body with structure:
                {
                  "data": {
                    "metrics": [
                      {
                        "name": "heart_rate",
                        "units": "count/min",
                        "data": [
                          { "qty": 72.0, "date": "2026-06-28 20:00:00 -0500", "source": "..." },
                          ...
                        ]
                      },
                      ...
                    ]
                  }
                }
  Logic:
    1. Parse the JSON body from the request
    2. Iterate over each metric in data["data"]["metrics"]
    3. For each metric, iterate over its data entries
    4. Extract the value using a fallback chain across Apple Health field variants:
         - qty       (most metrics: steps, calories, distance, etc.)
         - Avg       (heart rate, exported as Min/Max/Avg ranges)
         - totalSleep (sleep analysis, exported with sleep stage breakdown)
    5. Collect all rows into a list (avoids thousands of individual DB calls)
    6. Open a DuckDB connection
    7. Insert all rows in one batch using executemany()
    8. Close the connection
    9. Return a success response with a count of rows inserted
  Output:     { "status": "success", "received_at": "...", "rows_inserted": N }

GET /health/summary
  Purpose:    Return aggregated averages for every metric in the database
  Input:      None
  Logic:
    1. Open a DuckDB connection
    2. Run: SELECT metric, AVG(value), unit FROM health_metrics GROUP BY metric, unit
    3. Close the connection
    4. Return the results as JSON
  Output:     { "summary": [["metric_name", avg_value, "unit"], ...] }


KEY DESIGN DECISIONS
---------------------
1. Per-request DB connections
   Opening and closing a DuckDB connection per request rather than sharing
   one global connection prevents lock contention between concurrent requests.

2. Batch insert with executemany()
   Building a list of all rows in memory and inserting in one call is
   significantly faster than looping and calling execute() once per row,
   especially for large payloads (tens of thousands of rows).

3. Long table schema
   One row per measurement keeps the schema flexible and the GROUP BY query
   simple and uniform across all metric types.

4. No ORM
   DuckDB is accessed with raw SQL. For an analytical pipeline like this,
   raw SQL is clearer and more performant than an ORM abstraction.


HOW DATA FLOWS END TO END
--------------------------
  1. Apple Watch records health metrics throughout the day
  2. Health Auto Export app on iPhone bundles them into a JSON payload
  3. App sends HTTP POST to http://<machine-ip>:8080/health
  4. FastAPI receives the request and parses the JSON
  5. All data rows are extracted and batch-inserted into DuckDB
  6. Any client can query GET /health/summary to get live averages
